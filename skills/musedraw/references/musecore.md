# MuseCore · making the design decisions

Use for original explanatory work, a difficult composition, or revising a
visible design failure. The shared workflow is in [SKILL.md](../SKILL.md).
This reference develops its collaborating decisions; it is not another serial
pipeline and does not prescribe one picture, palette or production medium.

## Understand what the picture must do

Carry forward the user's audience, use, content facts, supplied assets/style,
delivery requirements and settled decisions. Separate the statements the work
must communicate from the material that supports them. A missing scientific
result, assignment or quantitative relationship cannot be invented for balance.

Choose the reader's first useful understanding. In a method architecture it may
be how several decisions jointly produce one plan; in a report it may be the
evidence for a conclusion; in a poster it may be an image that makes the occasion
recognisable. This gives visual weight a purpose beyond making a title large.

## Make a coherent proposal

Use expression judgement, visual conception and visual orchestration together.
Resolve these four aspects at the fidelity needed to start making the work:

| Aspect | A decision another maker can act on |
| --- | --- |
| Content structure | Which facts lead, which support them, and which relationships need to be visible? |
| Main visual | What actual object, image, spatial arrangement or graphic action conveys that understanding? |
| Visual language | How do type roles, image treatment, colour areas, edges, line weights and density work together? |
| Asset and medium responsibilities | Which parts are drawn, plotted, typeset, photographed/generated or interactive, and which source remains editable? |

“Editorial, restrained, premium” does not resolve these decisions. A useful
proposal might put one actual comparison at a readable scale, organise its
supporting evidence on the same axis, and reserve a contrasting typographic
voice for the interpretation. Choose from the content, rather than filling a
universal proposal template. Existing family sources in
[visual language](visual-language.md) can supply a complete vocabulary.

For a substantial original work, a few working notes can preserve the proposal
across making and revision. Use an artifact only when it helps the task; do not
print process labels, checklists or art-direction claims inside the artwork.

## Make relationships visible without tracing a reference

Give the composition a relationship to communicate before choosing its container:

| Relationship in the brief | Possible visual construction | Condition to preserve |
| --- | --- | --- |
| Several contributions jointly form one result | Contributions visibly meet in, act on, or make up the same result | A ring alone can imply a cycle; intersecting areas can imply shared membership. Choose the construction that matches the actual meaning. |
| One requirement applies throughout several activities | A shared field, enclosure or repeated local treatment spans those activities | A separate caption or final-stage box does not by itself show the scope. |
| A proposal selects different production routes | One proposal branches to the actual alternatives; routes rejoin where delivery is shared | Distinguish alternatives from mandatory parallel tasks and sequential stages. |
| Experience updates future work | A return route reaches the resource or decision that changes | Keep it subordinate to the current creation path; distinguish project facts from general methods. |

These are choices, not required motifs. Spatial contact is not appropriate for
every abstract dependency. An overlap must not imply mixing, a measured quantity
or an exclusive capability assignment that was not supplied. A familiar cycle,
table or rectangular module is appropriate when it expresses the real relationship.
Use [object composition](object-composition.md) for the corresponding constructions.

When learning from a supplied reference, retain the **linked decisions** that
make it work: what dominates, how objects differ, where density changes, what
colour does, and how typography belongs to those objects. Reconsider them for
the new content. Importing its circles, a dark centre or its palette alone is
neither a complete design method nor evidence of independent invention.

## Orchestrate the whole picture

Allocate space for the important relationship and its readable labels before
adding surface effects. A large abstract container with miniature facts inside
can consume attention without explaining the subject. Enlarging the container
again will not fix that imbalance. Compare its visual weight with what readers
must actually inspect.

Use consistent construction within a role and appropriate variation across
roles. A plan document, a physical object, evidence marks, an alternative route
and an enclosing scope can belong to one visual language without all becoming
matching cards. Conversely, matching objects are useful for true peers or a
controlled comparison. The point is a readable overall composition, not maximum
variety of shapes.

Coordinate the decisions rather than decorating after layout: colour area
affects balance, a font changes line lengths, labels require space, and an image
silhouette changes the reading path. Keep semantic phrases together when wrapping.
A valid bounding box can still contain an awkward isolated syllable. Draw
opaque backing objects before the marks they support; a correctly coded icon
hidden behind a later rectangle contributes nothing to the final picture.

## Make, inspect and return to the right decision

Choose the medium in the entrypoint. Existing semantic composers own geometry
only for their supported relationships; custom scenes, HTML, plotting and image
tools retain their appropriate roles. MuseCore does not automatically translate
an arbitrary proposal into a layout.

For requested visual testing or a visible failure, inspect the actual render:
can readers see the intended relationship, locate the important information and
read it at the delivery size? Keep factual and functional checks separate.
If the visual structure does not communicate, return to the proposal and change
that structure. Use local corrections for an actual local defect. A colour swap,
new border or additional explanatory paragraph will not necessarily repair a
weak composition.

When uncertain, make a small sketch or the hardest region first. Multiple
directions are useful only if their spatial organisation or visual idea differs
meaningfully. They are an optional way to resolve uncertainty, not a quota.
Preserve first/best versions and failures during continued development. Respect
the user's choice to judge the images themselves; extra agents or model votes
are not an obligatory review stage. See [visual revision](design-review.md).

## Separate memory, candidate methods and shared methods

- **Project memory:** the user's facts, assets, fixed choices and preferences.
  Keep these local to the project unless the user asks otherwise.
- **Candidate method:** a particular design decision with its applicable
  relationship, complete source/asset requirements, expected benefit and known
  failure. Label it experimental while it is being adjusted on a development task.
- **Shared method/style resource:** promote a candidate after trying new content,
  retaining the outcomes and boundaries. Preserve failed transfers. Include user
  judgement when claiming aesthetic improvement; file validation proves a different thing.

Private reference artwork is not automatically publishable. Replays, local
revisions, repeated views and downloaded files do not add independent successful
tasks. Record what was actually made and tested before claiming a portable benefit.
